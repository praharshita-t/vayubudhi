### 1.2 Finalized Data Sources (Ranked by Priority)

We need **3 layers** of data: (A) Ground-truth pollutant concentrations, (B) Atmospheric physics & weather, and (C) Contextual spatial enablers. The sources below work for Hyderabad AND generalize to any Indian city.

#### Layer A: Ground-Truth Air Quality Data

| # | Source | What It Gives Us | API / Access | Why This Source |
|---|---|---|---|---|
| **A1** | **Open-Meteo Air Quality API** | Hourly PM2.5, PM10, NO2, SO2, CO, O3, Aerosol Optical Depth (AOD) for ANY lat/lon in India. Historical + forecast. | `https://air-quality-api.open-meteo.com/v1/air-quality` — **Free, no API key, no rate limit** | Already used in [`fetch_data.py`](file:///c:/Users/Sai%20Koushik/Desktop/ET_Hackathon/vayubudhi/ml_model/src/fetch_data.py#L9-L62). Covers every district centroid without needing a physical station. Best for bulk historical backfill. |
| **A2** | **CPCB CAAQMS / TSPCB Portal** | Official government CAAQMS hourly readings for real stations (Sanathnagar, Zoo Park, Kompally, HCU, Patancheru, ICRISAT). | Scrape from [app.cpcbccr.com](https://app.cpcbccr.com) or [tspcb.cpcb.gov.in](https://tspcb.cpcb.gov.in) | Ground-truth calibration anchor. These are reference-grade instruments. Use to validate Open-Meteo satellite estimates against real sensor measurements. |
| **A3** | **OpenAQ Platform** | Aggregated open-source mirror of CPCB + global station data. Bulk CSV/Parquet dumps on AWS S3. | [openaq.org/developers](https://openaq.org) — Free API + S3 `openaq-data` bucket | Easiest automated bulk download for historical backfill (2+ years). > **Primary Pipeline:** Use **Open-Meteo (A1)** as the main data engine — it provides hourly data for any arbitrary lat/lon (all 33 Hyderabad districts + any Indian city) without physical station constraints. Use **CPCB (A2)** as ground-truth validation anchors for stations that exist. Use **OpenAQ (A3)** for bulk historical backfill to build multi-year seasonal patterns.

#### Layer B: Atmospheric Physics & Meteorology

| # | Source | What It Gives Us | API / Access | Why This Source |
|---|---|---|---|---|
| **B1** | **Open-Meteo ERA5 Weather API** | Hourly: Temperature, Humidity, Wind Speed (10m), Wind Direction, Surface Pressure, **Planetary Boundary Layer Height (PBLH)**, Cloud Cover, Precipitation | `https://archive-api.open-meteo.com/v1/era5` — **Free, no key** | Already used in [`fetch_pblh.py`](file:///c:/Users/Sai%20Koushik/Desktop/ET_Hackathon/vayubudhi/ml_model/src/fetch_pblh.py). | **B2** | **Open-Meteo Forecast API** | 7-day ahead NWP forecasts: Wind, PBLH, temperature, humidity at hourly resolution | `https://api.open-meteo.com/v1/forecast` — **Free** | Provides forward-looking weather features for the 24h/48h/72h ML prediction window. Without this, the model can only use "current" weather, not future atmospheric conditions. |
| **B3** | **ECMWF ERA5 via Copernicus CDS** (optional, advanced) | Research-grade 0.25 degree grid reanalysis: friction velocity, boundary layer dissipation, convective available potential energy (CAPE) | [cds.climate.copernicus.eu](https://cds.climate.copernicus.eu) — Free registration | Only needed if pursuing physics-informed deep-learning models. > **Key Insight:** Open-Meteo wraps the same ERA5 reanalysis data that ECMWF provides, but through a zero-friction REST API. For our use case, **B1 + B2 are sufficient** — we don't need to deal with CDS registration and NetCDF parsing unless we want raw 0.25 degree grid fields.

### 2.2 Finalized Model Stack

#### A. AQI Forecasting Models (Regression)

We will train **3 model families** for each horizon (24h, 48h, 72h) and select the best:

| Model | Library | Hyperparameters | Why Include It |
|---|---|---|---|
| **XGBoost** | `xgboost` | `n_estimators=300, max_depth=6, learning_rate=0.03, subsample=0.8, colsample_bytree=0.8` | Current baseline. Excellent on tabular data. Strong feature importance interpretability. |
| **LightGBM** | `lightgbm` | `num_leaves=31, learning_rate=0.03, n_estimators=300, min_child_samples=20` | Faster training, handles high-cardinality features (district IDs) natively. Leaf-wise splitting often outperforms XGBoost on large datasets. |
| **CatBoost** | `catboost` | `depth=6, iterations=300, learning_rate=0.03, l2_leaf_reg=3` | Native categorical feature support (district IDs without one-hot encoding). Robust against overfitting with ordered boosting. |

**Final Selection Strategy:**
```
1. Train all 3 models per horizon (9 models total)
2. Evaluate on held-out time-ordered test set
3. Select best single model per horizon (lowest RMSE)
4. ALSO create a Weighted Ensemble: 0.4 x Best + 0.35 x Second + 0.25 x Third
5. Pick whichever (single or ensemble) has lowest RMSE on test set
6. Wrap winner in MAPIE SplitConformalRegressor for 90% coverage intervals
```

#### B. Source Attribution Models (Classification)

| Model | Purpose | Improvement Over Current |
|---|---|---|
| **Random Forest Classifier** (keep) | Primary source classifier | Retrain with enriched features (NO2/SO2 ratios, FIRMS fire proximity, traffic density) instead of PM ratio heuristic |
| **Gradient Boosted Classifier (XGBoost)** (add) | Secondary benchmark | Often outperforms RF on imbalanced classes |
| **SHAP Explainer** (add) | Feature importance per prediction | Provides the waterfall chart showing WHY the model classified a source — critical for the Deep Dive dashboard |

**Source Categories (expanded from 4 to 5):**

| Category | Key Discriminating Signals |
|---|---|
| Vehicular | High PM2.5/PM10 ratio (>=0.70), elevated NO2, morning/evening diurnal peaks, high traffic density |
| Industrial | Elevated SO2, steady 24/7 emission profile, proximity to industrial zones |
| Dust / Construction | Low PM2.5/PM10 ratio (<=0.40), high PM10, dry + hot conditions, low humidity |
| Biomass Burning | Very high PM2.5/PM10 (>=0.85), high CO, FIRMS thermal anomalies nearby, low PBLH inversion |
| Secondary / Photochemical | High O3, high UV, afternoon peak, warm + humid conditions |

#### C. Conformal Prediction (Uncertainty Quantification)

| Component | Implementation |
|---|---|
| **Forecast Intervals** | `MAPIE SplitConformalRegressor` wrapping the winning model per horizon. Calibrated on a held-out chronological calibration set (15% of data). Target: 90% empirical coverage. |
| **Attribution Prediction Sets** | `MAPIE SplitConformalClassifier` wrapping the RF/XGB classifier. Outputs a set of plausible sources (e.g., `["vehicular", "industrial"]`) with 90% guaranteed coverage. |

### 2.3 Feature Engineering Pipeline

```
Raw Data (per row)
    |
    |-- INSTANT FEATURES (7):
    |   pm25, pm10, temp, humidity, pressure, wind_speed, pblh
    |
    |-- DERIVED PHYSICS (3):
    |   ventilation_index = pblh x wind_speed
    |   pm_ratio = pm25 / (pm10 + epsilon)
    |   stagnation_flag = 1 if VI < 2000 else 0
    |
    |-- TEMPORAL LAGS (6):
    |   pm25_lag_1h, pm25_lag_3h, pm25_lag_6h
    |   pm25_lag_12h, pm25_lag_24h, aqi_lag_24h
    |
    |-- ROLLING STATISTICS (4):
    |   pm25_rolling_6h_mean, pm25_rolling_24h_mean
    |   pm25_rolling_24h_std, pm25_delta_6h (current - 6h ago)
    |
    |-- CYCLIC TIME ENCODINGS (4):
    |   hour_sin, hour_cos, month_sin, month_cos
    |
    |-- POLLUTANT RATIOS (3):
    |   no2_so2_ratio = no2 / (so2 + epsilon)
    |   co_no2_ratio = co / (no2 + epsilon)
    |   o3_pm25_ratio = o3 / (pm25 + epsilon)
    |
    |-- SPATIAL CONTEXT (2):
        district_id (categorical)
        spatial_lag_pm25 = distance-weighted mean PM2.5 of 3 nearest districts
    -----------------------
    TOTAL: ~29 features
```

### 2.4 Train/Calibrate/Test Split (Zero Leakage)

```
Timeline ---------------------------------------------------------------->

[=========== TRAIN (70%) ===========][== CALIBRATE (15%) ==][=== TEST (15%) ===]
         Fits base models              Calibrates MAPIE        Final evaluation
                                       conformal intervals     vs persistence
                                                               baseline
```

> **CRITICAL: NO shuffling.** Data is split strictly chronologically. All districts share the same time cutoff. This prevents the catastrophic data leakage present in the current `train_test_split(shuffle=True, random_state=42)` call.
